# 对标参考与设计取舍

核对日期：2026-10-25。依据为厂商官方帮助、产品文档和更新说明；未登录竞品完整实测，不采用厂商宣传的准确率或效率作为本系统的效果证明。

## 1. 对标目的

本次对标关注操作模式：资料如何进入、分析内容如何配置、执行后在哪里看成果、如何核验来源、如何复用。目标是形成适合审计人员的工作方式，而非增加竞品功能数量。

| 参考产品 | 官方资料体现的模式 | 本系统的设计取向 | 保留的差异 |
| --- | --- | --- | --- |
| DataSnipper DocuMine | 对选定文档提出问题，在表格中阅读答案，通过来源引用核验 | 结构化成果优先，单条结果与原文连续核验 | 不依赖 Excel 才能完成操作；不通过拒绝答案删除原始 AI 输出 |
| 合合信息 TextIn DocFlow | 先配置类别、字段与规则，再在日常处理中复用 | 将可复用配置与日常批次分开，事实提取与规则核查连续承接 | 审计探索仍允许临时选资料、编辑本次提示词 |
| Hebbia Matrix | 选择资料，围绕研究问题组织列，筛选后继续分析或导出 | 资料×分析内容的批量成果、资料复用、来源信息 | 会议和台账关系保留专用结果，不全部改成矩阵 |
| Rossum | 队列组织资料类型，处理后复核，区分 AI 与人工验证 | 文件处理、人工核验与输出状态明确分工 | 不给临时分析增加强制审批和导出前置门槛 |

表中后两列是本系统的设计判断；产品事实依据见下文。

## 2. DataSnipper：问题—答案—证据

DocuMine 的基本操作是在 Excel 中提出问题，针对文档生成答案及来源引用，随后由使用者核验。可借鉴先获得结果、再就地查看依据的顺序。[官方入门](https://knowledge.datasnipper.com/en/articles/694313-getting-started-with-documine)

Focus Mode 在单条答案旁展示来源文档，支持前后切换和接受／拒绝。汇总表负责筛选，单条视图负责阅读上下文，这种分工适合连续核验。[Focus Mode 官方说明](https://knowledge.datasnipper.com/en/articles/714302-how-to-efficiently-review-answers-using-focus-mode)

会议纪要用例围绕预算决策、批准事项等提出问题，完成后核验带来源的答案。官方说明拒绝会移除答案及关联引用。本系统借鉴提问与核验，仍保留原始输出和独立人工意见。[会议纪要用例](https://knowledge.datasnipper.com/en/articles/714304-how-to-efficiently-review-board-minutes-with-documine)

**本系统的落实。** 信息提取保留资料×字段表；合同和招投标将检查事项、判断依据和原文放到连续核验视图，关闭后返回原筛选位置。会议保留更适合跨期事项的时间轴与议题聚类。局部修正某条结果后重跑，需要稳定结果标识和真实服务支持，不以页面模拟代替。

## 3. 合合信息：配置复用与连续处理

DocFlow 官方说明将文档处理组织为采集、解析、分类、抽取和审核，并支持原件与抽取内容对照。可参考完整业务链路，而非只模仿某张配置页。[产品流程说明](https://docs-docflow.textin.com/docflow/cn/00-overview/intro)

其已有工作空间的合同示例区分一次性配置与日常操作：已有类别和规则库后，重复上传合同、获取抽取内容、发起审核并取得结论。这是 API 场景说明，不能推断每一步都对应独立 UI 页面。[已有配置的合同处理](https://docs-docflow.textin.com/docflow/cn/00-overview/contract_review_already_configured)

**本系统的落实。** 系统／个人提示词和提取模板承载复用，本次工作区确认资料和检查内容。合同直接承接要素与检查结果，无须用户先去信息提取再搬运；费用提取与续算保持同一任务。资料空间沿用公共、项目、个人体系。

**设计取舍。** 稳定类别的处理模式不能直接替代审计临时探索。保留字段调整、本次提示词和再次分析，不把创建空间、训练类别、配置规则库变成每次使用的必经步骤。解析准确性、队列容量及模型质量仍需本系统自身验证。

## 4. Hebbia：批量比较与成果复用

Hebbia 官方更新介绍 Matrix 的资料选择与问题列创建、来源列、将筛选资料转入其他分析，以及 Excel 导出，可借鉴围绕明确问题组织批量成果的方式。[Matrix 创建及资料复用](https://www.hebbia.com/blog/the-disclosure-march-2026)

**本系统的落实。** 信息提取提供动态字段表，从分析记录复用资料时说明范围，再次分析沿用执行配置。列多时固定识别列、独立横向滚动及来源入口，不能缩小字号挤入全部字段。

**设计取舍。** 不新增与项目空间重复的概念，不要求用户编排 Agent。跨工具中间结果自动复用、局部重跑和结果合并，需后端明确契约后再做。

## 5. Rossum：处理与人工核验分工

Rossum 入门流程按队列组织不同类型资料；上传处理后，需要人工复核的资料进入待复核区域。验证页呈现抽取字段，并区分机器与人工验证。[官方入门与验证流程](https://knowledge-base.rossum.ai/help/docs/getting-started-with-rossum)

**本系统的落实。** 文件解析、任务执行、业务判断和人工核验采用四层状态。未命中不是执行失败，已完成不代表审计确认。人工意见与模型输出分开保存。

**设计取舍。** 原型核验记录仍在当前浏览器，不能假定已支持跨设备协作。正式版本先接真实身份和稳定结果 ID，再决定机构复核流程；本轮不增设强制审批。

## 6. 对标后的操作模式

建议采用“工具内完成业务，模板复用经验，来源支撑核验，任务中心管理历史与运行”的模式。

| 借鉴点 | 当前原型落地 | 正式落地条件 |
| --- | --- | --- |
| 成果与原文相邻 | 提取核验、合同／招投标连续证据视图 | 真实来源定位、权限和文件版本 |
| 配置复用 | 系统默认、个人另存、再次分析 | 模板／提示词持久化及版本兼容 |
| 本工具看结果 | 当前页进度与结果、工具内记录 | 真实轮询、刷新恢复、类型分派 |
| 大批量清晰管理 | 本页／全部页、分页、规则筛选、长文档按需显示 | 服务端选集契约、容量与性能实测 |
| 人工记录独立 | 可选核验意见 | 稳定结果 ID、真实身份和保存服务 |
| 局部重跑与自动流转 | 未作为已完成能力宣称 | 确认业务收益，再定义执行和合并契约 |

本次不因对标新增强制步骤、厂商依赖或采购要求。产品事实以链接页面为依据，应用方式须通过审计业务试用检验。
