# 文档挖掘助手总体优化设计方案

审计业务视角 · 产品流程与研发落地版

版本：V1.0　审查日期：2026-10-25　适用基线：前端原型 20261024.80

## 1. 总体结论

本系统应定位为“面向审计人员的文档分析与线索核验工作台”：帮助审计人员从大量文字资料中提取事实、识别关注事项、对照原文、形成可继续核查的成果。产品主线已经基本形成，后续工作的重点是收敛规范、回迁正式前端、接通真实服务与验证业务正确性。

日常操作统一为：**添加资料 → 设置分析内容 → 开始分析 → 查看结果 → 按需核验 → 导出成果**。查看原文是贯穿准备和结果的辅助能力；普通用户不必先理解调度、模型调用和任务类型编号。

这次优化主要改善的是操作组织、信息表达、资料范围管理和结果核验体验。原前端已提供多项分析工具及其服务调用、提示词配置、任务管理和专用结果组件，不应把这些既有能力描述为本轮新增。当前部署交付的是可交互前端原型，真实 AI 质量、生产并发、服务端权限与数据持久化尚不能由原型测试证明。

### 1.1 本次交付解决什么问题

| 评审问题 | 本方案给出的答案 |
| --- | --- |
| 系统为谁、完成什么事 | 以审计人员从资料中寻找事实、关联和异常线索的工作为中心；不同工具交付不同成果 |
| 哪些设计已确定 | 收敛步骤、资料选择、提示词、结果、任务中心、再次分析和 UI 规则，标注历史文档冲突 |
| 到底提升了什么 | 将每项提升对应到原有问题、当前实现和验证证据，不虚构节省时间或准确率 |
| 原功能有没有丢失 | 逐模块对照原 Vue 源码，保留业务阶段、专用载荷、参数量纲、结果类型与恢复流程 |
| 后端要改多少 | 优先沿用既有接口；分别列前端适配、服务能力确认、确有需要时的最小增补 |
| 下一步如何开发验收 | 给出实施批次、责任分工、阻断项、场景验收与正式联调的完成标准 |

## 2. 从审计工作反推产品设计

### 2.1 核心用户与职责

| 用户 | 核心诉求 | 产品应支持 |
| --- | --- | --- |
| 一线审计人员 | 快速确定资料范围，找到需要追查的事实和线索 | 明确本次已选资料、直接使用默认提示词、查看专用结果、追溯依据、导出 |
| 熟练审计人员／业务骨干 | 调整字段、规则和提示词，复用有效配置 | 本次编辑、另存个人提示词／提取模板、再次分析、保留原结果 |
| 项目复核人员 | 判断分析依据是否充分、是否存在遗漏 | 资料与配置快照、来源定位、人工核验意见、完整与部分完成的区别 |
| 管理及运维人员 | 管理资料归属与权限，排查积压和异常 | 服务端授权、任务状态与错误、阶段日志、队列监测；不把技术信息强加给普通用户 |

人工核验意见用于记录“已核对／存疑”及说明，不应自动改写模型原始输出，也不应把“已核对”直接解释为已形成审计定性。系统输出与审计发现之间仍有核实事实、补充证据和专业判断的过程。

### 2.2 三类典型工作

**批量获取事实。** 从合同中提取合同方、金额、日期及约定，形成可筛选的结构化表。审计人员关心字段是否适用、资料是否完整、单元格取值来自哪里。

**查找关系与异常。** 从会议决策、风险规则、合同和招投标资料中识别需要关注的事项。审计人员关心依据、适用条件、跨文件关系、时间顺序，以及未发现、未命中、执行失败的区别。

**核对与测算。** 从合同提取计费约定后填写基数，或比较台账中的重复项目、主子关系和两表候选关联。审计人员关心单位、字段映射、评分含义和源行，而不只是一个综合结论。

## 3. 设计理念与取舍

### 3.1 一个操作骨架，保留业务差异

共用资料选择、步骤标题、提示词编辑、执行反馈、历史记录、来源核验和导出方式；结果形态由业务决定。信息提取用字段表，词云用词频和词云，会议用时间轴与议题聚类，合同和招投标用检查事项，费用用计算报告，台账比较用候选关系与源行。

统一并不要求所有工具使用相同栏数。信息提取和配置相对简洁的工具允许边看资料边调整；规则、角色和映射复杂的工具把主要空间留给配置，原文按需打开。

### 3.2 先呈现本次工作，后呈现高级参数

第一眼回答三个问题：选了哪些资料、准备检查什么、下一步在哪里。执行方式、细分阈值、长提示词及报告附加设置在需要时展开。不能用省略号隐藏高频核心操作，也不能为了显得简洁而隐藏必填项和缺失原因。

### 3.3 用业务动作引导，不要求用户猜状态

步骤以动宾结构表达，例如“添加资料”“查看原文”“设置提取字段”“设置会议分析提示词”。提示词只称提示词，不夸大成分析方案。文档解析、AI 执行、业务结果和人工核验分别命名，避免同一个“完成”承担多种含义。

### 3.4 让结果成为工作的中心

执行后在当前工具查看进度和结果；离开后从本工具“分析记录”找回。任务中心作为跨工具统一入口，既能监测执行，也能打开对应成果，不复制第二套结果页面。查看某条结果时提供来源与连续切换，减少在列表、详情、原文之间反复进出。

### 3.5 默认可用，调整有边界

提示词工具进入时默认选择对应系统提示词，也可选择适配当前环节的个人提示词；组织和公共分类保留。替换提示词附带规则时先说明影响范围，只修改当前环节。

信息提取模板是特例：按已确认要求默认不选，由用户选择模板或填写字段。大量调整后的字段可以另存个人模板；本次编辑不静默修改公共或历史模板。

### 3.6 大批量交互不能改变执行范围

查找、分页、折叠、预览及屏幕切换只改变显示。执行使用完整本次资料、项目角色、规则和排除项。长正文按需呈现，但全文检索和导出不能只覆盖当前显示片段。

## 4. 信息架构与主流程

### 4.1 全局功能分工

| 区域 | 定位 | 与其他区域的关系 |
| --- | --- | --- |
| 资料管理 | 管理公共、项目、个人空间中的文件、目录、解析与权限 | 可选资料带入工具；文件移除与物理删除严格区分 |
| 11 项分析工具 | 本次业务操作、运行反馈与专用成果 | 可以直接添加资料、查看原文、配置和执行，无须绕到任务中心 |
| 提取模板 | 管理信息提取的字段及说明 | 在信息提取中选用；不作为全部工具的统一“方案库” |
| 提示词能力 | 提供公共／机构／个人提示词及本次编辑 | 接原提示词体系，按工具和环节过滤，不另造重复知识库 |
| 任务中心 | 跨工具分析记录、运行状态、任务信息与导出入口 | 三个核心操作：查看结果、任务信息、导出数据；结果分派回对应工具 |
| 上传／解析记录 | 管理资料入库与解析异常 | 解析完成不等于业务分析完成，不能与分析记录混为一谈 |

### 4.2 正常执行流程

1. 进入工具，或从资料管理带入资料；存在草稿时保留已有配置和归属，并明确追加／替换。
2. 添加本次资料；通用选择器只允许解析完成且满足权限、格式要求的文件，招投标和两表另校验角色。
3. 查看或调整字段、提示词、规则及业务参数；原文可看但不是必须的确认动作。
4. 点击“开始提取／开始分析”，提交摘要显示真实资料数量、关键配置和成果类型。
5. 以服务回执确认任务创建；在当前页显示排队、运行和阶段进度。是否前往任务中心独立于立即／排队执行。
6. 显示对应业务成果；部分完成允许查看已有结果，同时说明缺项及恢复入口。
7. 按需核验来源、筛选和导出；如需调整，点击“再次分析”进入沿用资料和配置的可编辑准备页，提交后建立新记录。

步骤标题是工作区域的导航，不是必须依次点击的审批流程。不得要求用户先逐份查看原文才能执行。

### 4.3 必须保留的特殊流程

| 场景 | 正确处理 |
| --- | --- |
| 主题归纳 | 基础信息提取与主题归纳是独立业务阶段；显示各阶段状态及可用成果 |
| 会议纪要 | 常规结果是后续风险分析和问答的基础；会议时间轴、议题聚类与筛选继续保留 |
| 待摊费用 | 提取约定 → 待填写计费基数 → 继续计算 → 查看报告，属于同一任务续办 |
| 招投标 | 以项目、招标文件、投标单位及投标文件组织；三种分析模式各自校验资料和规则 |
| 工程项目一致性 | 逐份台账内部识别重复／主子项目，不能暗示自动完成任意跨台账对比 |
| 两表项目关联度 | 显式指定两表角色、字段映射与比较规则，保留候选、两侧源行及二次筛选恢复 |
| 失败重试 | 只重试服务确认的失败对象；与修改配置后新建分析区分，不能覆盖成功结果 |

### 4.4 统一四层状态

| 层级 | 示例 | 用户可以推断什么 |
| --- | --- | --- |
| 文件处理 | 未解析、解析中、解析完成、解析失败 | 文件是否具备进入分析的基础；不代表任何工具已分析 |
| 任务执行 | 待提交、等待执行、执行中、部分完成、失败、已停止、已完成 | 本次请求执行到哪里；等待时间不等于系统卡死 |
| 业务阶段／结论 | 待填计费基数、报告生成中、未发现、存在疑点、不适用 | 业务如何继续、结果如何解释；不适用不是系统错误 |
| 人工核验 | 未记录、已核对、存疑 | 审计人员是否留下核验记录；独立于 AI 输出与任务状态 |

后台未提供真实排队位置、进度或剩余时间时，不伪造确定数字；断线显示最后状态及刷新方式。停止、删除、再次分析和重试各有不同语义，服务能力确认前不能用其中一个接口替代另一个。

## 5. 工作区与交互设计

### 5.1 准备页布局

| 工具组 | 桌面布局 | 设计原因 |
| --- | --- | --- |
| 信息提取 | 添加资料／查看原文／设置提取字段 | 字段常需对照原文即时调整 |
| 词云、主题、时间轴、风险点、会议、待摊费用 | 添加资料／查看原文／业务设置 | 沿用相同工作习惯；风险点在设置区内另用检索分页处理大清单 |
| 合同、招投标、工程一致性、两表关联 | 资料及角色／宽配置区；原文按需打开 | 规则、项目关系、字段映射需要较大可操作空间 |
| 结果页 | 业务成果主区＋按需来源核验 | 不保留准备态的左侧资料清单；让结果占主要空间 |

三栏按可用容器宽度适配，窄屏通过面板页签切换，不把全部列缩小挤在一起。当前原文区没有“收起原文”操作，旧隐藏状态自动恢复。步骤、文件名、原件／解析切换合并为紧凑页头，PDF 翻页缩放独立成一行。

### 5.2 资料选择与范围

统一把跨页选择反馈放在列表顶部：表头勾选只选本页；提示中提供“选择全部页”并显示当前筛选总数。跨目录已选保留；变化后继续清楚说明实际已选范围。目录搜索与文件搜索分工明确，中文输入法组合期间不重建输入框。

工具左侧清单就是本次已选资料，不再同时展示多份含义相同的“已选文件”。关联附件和移除保留紧凑图标与文字提示；附件属于指定主文件，移除只取消本次选择。资料库管理页的批量管理与工具准备页的逐份移除分别按场景处理，不能机械删除整个系统的批量能力。

### 5.3 提示词与规则

正文编辑空间优先，名称、分类和说明压缩；固定底部应用／取消操作。编辑尚未应用的草稿与已应用配置分离。个人另存、恢复默认、只读历史各有明确状态。

大量规则采用检索、分类、分页、已选数量和规则详情，不平铺数十个长标签。选择提示词时若附带规则，明确替换的业务环节和条数；保留当前项目、资料及其他环节。

### 5.4 结果与来源

结果页共用“再次分析”和“导出”，不恢复低频配置导入导出和重复的“本次配置”按钮。任务信息保存实际执行快照，用户需要重新调整时直接进入再次分析。

核验页面同时呈现事项、判断依据与来源；合同、招投标支持在当前筛选结果内连续前后查看，关闭返回原列表位置。有真实页码、文本锚点或坐标时才精确定位；只有文件 ID 时提供文件级查看，不伪造高亮。

## 6. 系统具体提升了什么

| 维度 | 原有使用负担／风险 | 当前前端改善 | 证明及仍需验证的内容 |
| --- | --- | --- | --- |
| 新人上手 | 工具、配置、资料和任务概念混在一起 | 动宾步骤、单一主操作、真实范围摘要、业务成果说明 | 当前界面可操作；首次使用完成率需用户测试 |
| 路径连续 | 容易理解成必须去任务中心才能看结果 | 当前工具承接进度和结果，本工具记录就近找回 | `in-tool-records-checks.json`；生产刷新恢复需联调 |
| 范围准确 | 本页、全部页、目录范围和预览容易混淆 | 顶部统一选择反馈，分页／折叠不影响完整执行范围 | 选择专项与大批量回归；大目录真实筛选需后台验证 |
| 长文档阅读 | 多行工具栏挤占正文，重渲染丢阅读位置 | 紧凑页头、按需解析文本、阅读会话保持、双栏放大 | 现行头部 44px，PDF控制行39px的测量；不由此推断总效率比例 |
| 配置复用 | 从头填写或修改历史配置 | 系统／个人提示词、本次副本、个人另存、再次分析 | 十一工具回归；服务端快照及版本需要明确契约 |
| 专业结果 | 不同工具容易被统一成通用列表 | 保留会议时间轴、聚类、检查依据、费用阶段和台账关系 | 各工具专项；算法准确率没有在本轮重新评测 |
| 连续核验 | 结果详情和原文反复切换 | 结果与依据同屏、当前筛选内前后切换、可选核验意见 | `integrated-evidence-checks.json`；意见持久化尚需服务 |
| 大批量可用 | 多文件、多规则、大正文占满界面 | 清单分页、规则检索、按段阅读、执行范围独立 | 历史模拟1500文件和约84万字；不能视为生产容量承诺 |
| 历史可追溯 | 重新操作可能覆盖原结果或被词库变更影响 | 输入与附件快照、再次分析建立新记录、原结果保留 | `result-reanalysis-checks.json`；实际数据版本需联调 |
| 交付可维护 | 多轮试验说明分散，旧规则冲突 | 本方案统一现行口径、提出组件化与接入分工 | 本轮文档交付完成；正式 Vue 回迁是下一阶段 |

## 7. 正式系统实现方式

### 7.1 继承现有工程，分层回迁

现行原型以多层脚本覆盖实现迭代，`index.html` 加载59个脚本及46份样式，其中含基础能力和第三方资源。它适合交互评审，但不适合作为正式工程长期维护结构。建议将确认后的页面和状态机迁回现有 Vue 组件，保留已有 API 服务及专用结果解析。

建议分层：

1. **业务页面层**：资料管理、各工具准备／结果、任务中心、提取模板。
2. **共用组件层**：资料选择器、已选清单、原文查看器、提示词编辑、规则选择、任务进度、来源核验、导出。
3. **领域适配层**：每工具的资料角色、配置校验、提交载荷、阶段解释和结果呈现；不能把十一工具压成一套通用字段。
4. **服务层**：复用现有任务、文件、模板、提示词、报告和导出 API；统一超时、回执、鉴权与错误处理。
5. **可观测与验收层**：关键状态日志、请求契约对照、异常恢复、性能与可用性场景。

不为外观统一改写后端任务编号或算法结构。原型的 `config-schema.js` 用于诊断映射，不是全部生产请求的替代品。

### 7.2 最小后端改动原则

先列出已有服务能满足的能力，再检查缺口。文件分页、任务创建与查询、结果详情、失败重试、模板及提示词管理优先复用。某 API 在前端被调用，只能证明原前端依赖该契约；未取得服务端实现或联调结果前，不保证服务现状。

重点确认：资料范围与解析资格、任务和业务类型识别、阶段及停止语义、配置快照完整性、来源定位、费用单位、历史导出、跨用户核验意见持久化。详见后端清单中的源码位置、载荷字段、责任与验收。

### 7.3 实施次序

| 批次 | 交付目标 | 进入下一批的条件 |
| --- | --- | --- |
| A 规范收敛与契约确认 | 确定本方案基线，补齐缺失 API 资料，确认 P0 单位／范围／状态约定 | 前后端能用同一份真实样例解释请求与结果 |
| B 共用能力回迁 | 资料选择、提示词、原文、任务状态和结果框架接入正式工程 | 小样本正常与异常链路均能走完，旧功能无回归 |
| C 逐工具落地 | 先信息提取／通用工具，再会议／风险，再合同／招投标／费用／台账 | 每工具输入、配置、结果、来源、导出、再次分析闭环 |
| D 生产验证与推广 | 真实权限、多用户、队列、长文档、大表、可用性测试 | 验收矩阵通过，问题有责任人和关闭证据 |

此处是依赖顺序，不是未经团队估算的工期承诺。后续按开发资源与真实接口缺口拆分迭代。

## 8. 本轮 review 的总体判断

现行原型在整体流程、页面一致性和业务成果保留方面已具备可用于评审与研发回迁的基础。本轮新鲜检查覆盖33个准备态布局，无页面级横向溢出和脚本错误，并复核了可用历史结果的打开与快照保持；这不能替代生产服务和真实审计效果验收。

当前最值得优先投入的四件事是：**消除文档基线冲突、解决接口契约关键不确定项、修正已发现的低对比度文字、完成正式 Vue 工程和真实服务的闭环联调**。不建议继续通过堆叠按钮、重复配置入口或统一所有结果版式来“增强”系统。

完整模块对照、UI 规则、后端清单、整改验收与对标来源分别见本目录02—06号文档。本方案与历史说明冲突时，产品口径以本方案所列现行基线和后续明确变更为准；源码调用事实以对应版本代码及服务联调证据为准。
