# 目录拖动排序：原代码核对与实现

## 原有规则

- `前端代码/views/file-manager-code/Index.vue:107–116`：树的 draggable 由 `isSuperFileAdmin()` 控制，空间根节点不允许拖动。
- 同文件 `allowFolderDrop`（约 4830 行）：只允许父节点相同的文件夹前后排序，禁止 inner 放入子级，禁止放在空间根节点前后。
- 同文件 `handleFolderDrop`（约 4870 行）：只保存 PUBLIC / PERSONAL。项目树虽可能触发拖动，但处理函数提前返回，未形成持久化排序；本次不将其扩展成项目空间的新接口需求。
- `前端代码/api/fileManager.js:191`：沿用 PUT `/api/v1/file-manager/folders/order`。

## 本次实现

左侧目录对有权限的超级文件管理员显示六点拖动手柄，整行可拖。指向同级目标上半行或下半行时显示蓝色插入线；松开后保存顺序。根目录不显示手柄，普通用户和项目空间不开放排序。公开只读或归档目录的排序只改变位置，不授予内容修改权限。

保留目录菜单“同级上移 / 同级下移”；手柄获得焦点后可按 Alt + ↑ / ↓。三种入口使用同一套规则。不同父目录、跨空间、自身投放、取消拖动、权限失效均不改顺序。外部文件拖放不触发目录排序。

保存完整同级列表，不能仅提交搜索后可见的节点。当前目录、文件路径、资料关联、勾选项和树的展开状态保持不变；资料选择器也沿用同一目录顺序。当前实现按浏览器本地存储保存，与其他页面状态一致。

## 正式后台对接

本次未改原始前端代码和后台。正式接入继续使用既有 `updateFolderOrderAPI({parent_folder_id, folder_ids, space_type})`；根层 parent_folder_id 为 null，folder_ids 必须为该父目录的完整、有序后台 ID，不能以显示名称或目录路径代替。聚焦视图需要从节点数据恢复真实父 ID。提交前再次校验身份与父目录；成功后确认顺序，失败则按原逻辑重新加载目录并保留展开节点，不能显示保存成功。共享顺序和服务端授权仍由原接口负责。
