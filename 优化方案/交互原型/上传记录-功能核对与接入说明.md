# 上传记录：原功能核对与接入说明

日期：2026-10-18。依据用户提供的「文件上传记录」截图，以及原 `views/file-manager-code/FileContentProgressPrototype.vue`、`api/fileManager.js` 核对。原前端代码、截图和业务材料未修改。

## 本轮结果

资料管理的文件名搜索框收窄为约160px，窄区域约112px；当前位置取得剩余宽度，保留完整路径提示和末级目录可见性。继续保持单条操作栏、16px业务字号和独立表格滚动。

上传记录采用空间切换后的全宽单列表，代替截图中的左右分栏；公共、项目、个人顺序保持一致。上传记录查询与资料列表搜索互不影响，不更改原文件或本次分析范围。

## 原接口保持不变

| 能力 | 原接口与参数 |
| --- | --- |
| 汇总 | GET `/api/v1/file-manager/content-progress/summary`，`space` |
| 记录列表 | GET `/api/v1/file-manager/content-progress/files`，`space/page/page_size/status/source/keyword` |
| 并发读取/保存 | GET/PUT `/api/v1/file-manager/content-progress/ocr-concurrency`；保存`concurrency_local/concurrency_oss`；读取`max_concurrency_local/max_concurrency_oss` |
| 选定记录重新入队 | POST `/api/v1/file-manager/content-progress/requeue-by-ids`，`file_ids/space` |
| 本地空全文批量入队 | POST `/api/v1/file-manager/content-progress/requeue-local-empty`，`space` |
| OSS补全文 | POST `/api/v1/oss/refresh-file-content` |
| 清空队列 | POST `/api/v1/file-manager/content-progress/ocr-queue/clear`，`clear_local/clear_oss/clear_processing/clear_failed` |
| 打开全文 | 继续使用`getFileContentAPI(file_id)` |

正式接入复用原API封装和角色`super_file_admin`，无需为布局改变后台上传/OCR逻辑。保留服务返回的入队数、推送失败、未找到、超最大重试、跳过处理中/已入队、批次截断等反馈；不能把HTTP成功当作每个文件识别成功。

原上传记录接口查询明确使用PUBLIC/PERSONAL。项目/全部为现有原型的扩展查看入口，正式联调须按原后台返回的资料归属与现有项目权限关联，不直接给接口新增未经支持的PROJECT值。界面的“失败/积压”组合条件也不是新增后台状态枚举。

## 实现与验证边界

本轮仍是浏览器中的高保真交互：真正读取和保存本地原文件，实际执行已有PDF、DOCX、表格和文本解析；以本地队列验证并发、重试、取消排队、权限和状态流转。未连接内网文件服务、OSS、Redis或OCR Worker，因此不将本轮验证称为正式服务联调，也不对后台队列或原业务资料执行清空操作。

截图中的海量总数、OSS全量数量、实际Redis标记、服务端最大重试次数、批次截断/失败反馈，必须由原后台接口返回，不能在前端编造。前端只显示已知记录与真实处理结果；原文件缺失时提示补充，不跳转成已完成。

验证证据：

- `review/upload-records-results.json`：12组实际浏览器检查。
- `review/folder-upload-results.json`：13组文件夹上传回归。
- `review/library-height-results.json`：12个窗口状态和1个框架嵌入场景。
- `review/compact-actions-checks.json`：单行操作栏、筛选收纳、菜单与权限回归。

新增视图由`dist/library-records.js`和`dist/library-records.css`维护；原文件选择、解析器、目录和权限规则继续复用既有实现。
